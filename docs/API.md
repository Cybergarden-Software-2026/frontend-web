# Backend API для underCtrl

Контракт React-клиента и Rust API дашборда. В режиме демо тот же интерфейс обслуживает локальный адаптер `tools/demo-api`.

## 1. Адрес и подключение

Базовый префикс: `/api/v1`.
Все JSON-ответы: `Content-Type: application/json; charset=utf-8`.

В `.env` фронтенда:

```dotenv
VITE_API_BASE_URL=/api/v1
VITE_API_PROXY_TARGET=http://localhost:8080
```

Второй параметр используется только Vite-прокси для локальной разработки. Можно указать полный URL в `VITE_API_BASE_URL`, если backend разрешает CORS для frontend origin. Секреты и ключи LLM во frontend environment не передаются.

## 2. Какие маршруты действительно нужны

### Обязательные для текущей версии фронтенда

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/v1/incidents` | Страница очереди: `page`, `pageSize`, `group`, `q`, `team`, `priority`, `status`, `sla`, `sort` |
| GET | `/api/v1/teams` | Справочник доступных для назначения команд |
| POST | `/api/v1/incidents/{sysId}/assignment` | Назначение выбранной команды с проверкой версии |
| GET | `/api/v1/snapshot` | Первичная загрузка и ручное обновление полного снимка, событий и состояния источника |
| GET | `/api/v1/events/stream` | Автоматические обновления через SSE; событие `snapshot` содержит новый полный снимок |
| GET | `/api/v1/incidents/{sysId}/analysis` | Разбор выбранного инцидента: выжимка, факты, признаки внимания, кандидаты команд и недостающие данные |

Очередь загружает страницы через API. Полный снимок пока используется для офлайн-кэша, счётчиков, хедера, карточек и аналитики. Это действующий контракт дашборда; для больших объёмов потребуется заменить полные SSE-снимки частичными изменениями и серверными агрегатами.

### Рекомендуемые для истории, больших объёмов и дальнейшего развития

| Метод | URL | Назначение | Состояние |
|---|---|---|---|
| GET | `/api/v1/incidents/{sysId}` | Отдельная актуальная карточка | Поддерживается демо API; текущий UI уже получает карточку в снимке |
| GET | `/api/v1/events` | Журнал, фильтры `afterId`, `beforeId`, `type`, `incidentSysId`, `limit` | Демо отдаёт последние 200 событий; пагинацию нужно согласовать |
| GET | `/api/v1/incidents/{sysId}/events` | История конкретного инцидента | Поддерживается демо API; UI пока показывает историю из снимка |
| POST | `/api/v1/incidents/{sysId}/analysis` | Обновить или явно запустить разбор | Демо поддерживает синхронный результат; кнопка повторного запуска в UI пока не требуется |
| GET | `/api/v1/problems/clusters` | Подтверждаемые гипотезы массовых сбоев | Демо API поддерживает; UI пока вычисляет по полному снимку |
| GET | `/api/v1/analytics` | Агрегаты по периоду и команде, если полной выгрузки на клиенте больше нет | Расширение; сейчас расчёт по текущему полному снимку |

Для новой главной обязательны шесть маршрутов из первой таблицы. Маршрут кластеров можно подключить позже: сейчас интерфейс выявляет совпадения по полученному снимку.

## 3. GET /snapshot

Ответ `200`:

```json
{
  "revision": 42,
  "serverTime": "2026-11-20T14:30:00.000Z",
  "updatedAt": "2026-11-20T14:29:58.000Z",
  "items": [],
  "events": [],
  "source": {
    "path": "ITSM / источник инцидентов",
    "readAt": "2026-11-20T14:29:59.000Z",
    "error": null
  },
  "itsmUrlTemplate": "https://itsm.example/incidents/{sysId}"
}
```

В примере массивы пустые только для краткости. `items` — полный массив исходных инцидентов. `events` — последние события, новые первыми.

| Поле | Тип | Правило |
|---|---|---|
| revision | integer | Монотонно растущая версия снимка; меняется при существенном изменении данных |
| serverTime | ISO 8601 string | Текущее время сервера с часовым поясом, используется для коррекции таймеров |
| updatedAt | ISO 8601 string | Время обнаружения последнего изменения снимка |
| items | Incident[] | Полный согласованный снимок, не одна страница |
| events | ChangeEvent[] | Последние события, новые первыми; идентификаторы стабильны |
| source.path | string | Читаемое имя источника; полный серверный путь в production не требуется |
| source.readAt | string или null | Последняя успешная проверка/загрузка исходного источника |
| source.error | string или null | Ошибка чтения источника; предыдущие корректные items сохраняются |
| itsmUrlTemplate | string или null | HTTPS-шаблон ссылки: `{sysId}` и/или `{id}` заменяются URL-encoded идентификатором |

`updatedAt` — серверное время наблюдения, не вымышленное время изменения в ITSM. В исходной выгрузке полноценного `updatedAt` записи нет.

Пустой `items: []` должен означать подтверждённый пустой полный снимок, а не ошибку чтения. При ошибке источника возвращается предыдущий снимок с `source.error`.

Сохраняйте все имеющиеся исходные поля; дополнительные поля разрешены. Идентификаторы — строки. `deadline`, `completionDate`, `serviceId` и другие исходно nullable значения не нужно заменять выдуманными данными.

В Rust API веб-клиент добавляет `?view=web` к `/snapshot` и `/events/stream`. У каждой записи в `items` появляется объект `dashboard.sourceDates` с полями `submitDate`, `deadline`, `completionDate` и `lastAssignmentToTeamDateTime`. Эти значения содержат UTC-время с учётом настройки импортёра `SOURCE_NAIVE_TIMEZONE`. Отсутствующая дата передаётся как `null`. Постраничная очередь и ответ на назначение команды включают эти же поля. Браузер использует их для сортировки, расчёта SLA и ожидания команды.

### Статусы: подтверждённая бизнес-семантика

| stateEnum | stateId в фактической выгрузке | Подпись | Значение |
|---|---:|---|---|
| Assigned | 0 | Назначен | Начало работы статусом не подтверждено; ответственные определяются отдельными полями |
| WorkInProgress | 2 | Выполняется | Идёт работа |
| Resolved | 7 | Завершён | Проблема устранена, но инцидент может быть возвращён в работу |
| Closed | 10 | Закрыт | Вся работа с инцидентом окончена |
| Research | 20 | Исследование ситуации | Отдельная группа; исключается из активных critical/high, может оставаться на координаторах |

В присланном справочнике ID 7 и 10 перепутаны относительно фактического JSON. Для контракта используем фактический `stateEnum` и указанное выше соответствие. Новые неизвестные статусы нужно передавать как есть; весь снимок из-за одного нового статуса не теряется.

`solution` — текст описания решения. Он может быть заполнен до завершения и содержать прошлую неуспешную попытку. По нему нельзя определять статус или обучать метку успешного решения без проверки. Наличие текста не означает, что проблема устранена. Поле могло остаться не полностью обезличенным: не отправлять его внешнему LLM-провайдеру автоматически без согласования политики обработки.

### Приоритет, срочность и влияние

`priorityId`: 1 — низкий, 2 — средний, 3 — высокий, 4 — наивысший/критический.
`urgencyId` и `impactId` — отдельные шкалы; их значение 4 само по себе не делает инцидент критическим.

### Группы дашборда

Внимание требуют Assigned, WorkInProgress и Research. Группы пересекаются:

- `critical`: priorityId = 4 и stateEnum = Assigned/WorkInProgress.
- `coordinators`: assignedGroupName = `КЦ ИТ Координаторы Массовых Инцидентов` и требуется внимание.
- `high`: priorityId = 3 и stateEnum = Assigned/WorkInProgress.
- `research`: stateEnum = Research.

Resolved и Closed доступны через фильтры статуса и SLA. Суммировать четыре счётчика как количество уникальных записей нельзя.

## 4. GET /events/stream — живые обновления

SSE: `Content-Type: text/event-stream`, без кеширования и буферизации reverse proxy.

При подключении сервер сразу отправляет актуальный полный снимок. Затем — новый полный снимок при изменении статуса, команды, приоритета, дедлайна, исполнителя или других отслеживаемых данных.

```text
retry: 2000
id: 42
event: snapshot
data: {"revision":42,"serverTime":"...","updatedAt":"...","items":[...],"events":[...],"source":{"path":"ITSM","readAt":"...","error":null},"itsmUrlTemplate":null}

```

`data` в примере схематична; в реальном потоке это одна строка валидного JSON формата Snapshot. Пустая строка завершает SSE-событие.

Heartbeat, например каждые 15 секунд:

```text
: heartbeat

```

Браузер переподключается автоматически. После переподключения сервер снова отправляет свежий снимок, поэтому карточки не зависят от полноты доставки промежуточных пакетов.
Для полного восстановления длинной истории необходим отдельный GET /events с курсором; текущий демо-клиент ограничивает вложенную в snapshot ленту последними 200 событиями.

Сервер не должен ждать LLM для отправки критического события. При повторной передаче идентификаторы событий не меняются.

## 5. ChangeEvent — событие изменения

```json
{
  "eventId": 105,
  "revision": 42,
  "sysId": "179413934903718013",
  "incidentId": "INC000021931151",
  "header": "Отказ Объектив (Камера-сканер)",
  "types": ["critical", "priority", "deadline"],
  "fields": ["priorityId", "priority", "deadline"],
  "at": "2026-11-20T14:29:58.000Z",
  "previous": null,
  "current": null
}
```

`previous` и `current` в реальных событиях содержат предыдущую и текущую запись. `previous = null` у новой записи. `current = null` при удалении. Пример выше показывает форму, а не конкретное изменение.

Типы: `created`, `critical`, `assigned`, `resolved`, `closed`, `reopened`, `research`, `deadline`, `team`, `priority`, `changed`, `removed`.

Одно изменение может иметь несколько типов. Например, изменение приоритета и команды одновременно должно дать одно событие со стабильным eventId и несколькими types, а не повторные оповещения по каждой группе.

Важно:

- `resolved` — переход в Resolved, `closed` — переход в Closed.
- `reopened` — возврат в работу после устранения/исследования.
- `assigned` — назначение именно группе координаторов, не любая смена команды.
- `critical` — новая критическая запись, повышение до 4 или возврат критического инцидента в поле внимания.
- `removed` — удаление из подтверждённого снимка; оно не означает решение.
- первичная загрузка архива не должна создавать десятки «новых критических» уведомлений.

## 6. GET /incidents/{sysId}/analysis

Возвращает готовый разбор. Для MVP допустим синхронный 200. Если LLM вызывается асинхронно, нужно отдельно согласовать состояния `pending/ready/failed` и доработать адаптер фронтенда; не возвращать незадокументированный 202 вместо Analysis.

```json
{
  "sysId": "179413934903718013",
  "revision": 42,
  "generatedAt": "2026-11-20T14:30:00.000Z",
  "provider": "llm",
  "summary": "Краткая выжимка на основании фактов инцидента.",
  "facts": [
    {"label": "Продукт", "value": "Название продукта"},
    {"label": "Статус", "value": "Назначен"}
  ],
  "attention": [
    "Назначен координаторам: нужно определить команду передачи."
  ],
  "candidates": [
    {
      "team": "Название команды",
      "evidenceIds": ["INC000000000001"],
      "reason": "Почему эта команда предложена и на каких данных основано предположение."
    }
  ],
  "missing": ["Не хватает справочника зон ответственности."]
}
```

`provider` — `rules` для объяснимого анализа без LLM, `llm` для настоящей модели. Не выдавать подготовленный текст или эвристики за результат модели.

Если оснований для рекомендации нет, `candidates: []` и объяснение в `missing`. Не выдумывать ссылки, зоны ответственности или вероятности эскалации. `revision` привязывает разбор к исходному снимку; после изменения инцидента предыдущий анализ должен считаться устаревшим.

`solution` можно показывать пользователю как описание попытки решения. Нельзя трактовать его как подтверждённый успешный результат, если статус этого не подтверждает.

## 7. Дополнительные ответы

GET /incidents (параметры и пример запроса — ниже):

```json
{"items": [], "total": 44, "page": 1, "pageSize": 9, "totalPages": 5, "revision": 42}
```

items содержит текущую страницу полных Incident, total — размер выборки после фильтров. Пустой items в примере используется для краткости.

GET /incidents/{sysId}:

```json
{"incident": {}, "revision": 42, "normalizedState": "Assigned"}
```

`incident` содержит полный Incident, а не пустой объект.

GET /events и GET /incidents/{sysId}/events:

```json
{"items": [], "nextCursor": null}
```

Для будущей курсорной пагинации истории курсор должен быть связан с согласованным порядком событий. Отсутствие записи на странице не означает удаление. Фронтенд под текущий полный снимок нельзя незаметно перевести на одну страницу.

## 8. Ошибки

```json
{"error": "Инцидент не найден", "code": "INCIDENT_NOT_FOUND"}
```

- 400: некорректные параметры/JSON.
- 401: сессия отсутствует или истекла, если есть авторизация.
- 403: недостаточно прав.
- 404: запись не найдена.
- 409: конфликт expectedRevision или запрещённое назначение завершённого/закрытого инцидента.
- 429: ограничение запросов.
- 500/503: сервер/внешний источник недоступен.

Ошибка источника при наличии кэша не должна превращать Snapshot.items в пустой массив.

## 9. Назначение и интеграция источника

Назначение команды уже требуется UI: POST /incidents/{sysId}/assignment, контракт описан ниже. Редактирование произвольных полей и статусов из UI пока не требуется. Изменения из ITSM или внешнего источника backend принимает своим интеграционным способом и публикует новый снимок через SSE.

В демо API есть:

- PUT /api/v1/incidents — заменить весь тестовый снимок валидным массивом.
- POST /api/v1/incidents — добавить/обновить полные записи по sysId.
- PATCH /api/v1/incidents/{sysId} — изменить поля записи.
- POST /api/v1/demo с action — только демонстрация изменения тестового файла.

Рабочему backend не нужен `/demo`. Полная замена данных через PUT и тестовые сценарии не нужны для обычной работы текущего UI. Для назначения backend проверяет права, версию снимка и ведёт аудит; способ внешнего обновления источника согласовывается отдельно.

## 10. Приёмочные проверки для backend

1. GET /snapshot возвращает предоставленную выгрузку без потери Research, null-дедлайнов и текста solution.
2. Изменение только deadline вызывает новую revision и SSE-обновление.
3. priorityId=4 у Assigned/WorkInProgress вызывает критический сигнал; Research с тем же приоритетом и urgencyId=4 при priorityId=2 — нет.
4. Критический инцидент на координаторах виден в двух группах.
5. Resolved, Closed и возврат в WorkInProgress различаются.
6. Заполненный solution не меняет статус.
7. Некорректный промежуточный JSON не стирает предыдущий снимок.
8. После переподключения SSE клиент получает актуальные данные.
9. События имеют стабильные IDs, повторные пакеты не дублируют историю и подсветку полей.
10. ИИ-результат содержит основания и версию исходных данных; сбой модели не блокирует обновление инцидентов.


## Новая главная: пагинация, назначения и массовые проблемы

### GET /incidents

Параметры: `page` (от 1), `pageSize` (9 по умолчанию, максимум 100), `group` (`all`, `critical`, `coordinators`, `research`, `high`; API также принимает `resolved`, `closed`), `q`, `team`, `priority`, `status`, `sla`, `sort` (`priority`, `deadline`, `newest`). Поиск и фильтры применяются перед пагинацией. Сортировка стабильна, последний ключ — номер инцидента.

Ответ: `{ "items": [], "total": 44, "page": 1, "pageSize": 9, "totalPages": 5, "revision": 12 }`.
`total` — число записей после фильтрации. Пустая выборка возвращает страницу 1 и totalPages 1; номер за пределами диапазона приводится к последней странице.

В макете P1 — наивысший приоритет, P4 — низкий. Отображение: `P = 5 - priorityId`; данные источника остаются прежними: 4 — наивысший, 1 — низкий. Справочник источника менять нельзя.

### GET /teams

Ответ: `{ "items": [{ "name": "Команда X", "activeCount": 3 }], "revision": 12 }`.
Rust API хранит справочник в таблице `teams`. Импорт пополняет её именами команд, и они остаются доступны при нулевой нагрузке. Администратор также может добавить команду до первого назначения. Локальное демо строит его из снимка и исключает техническую группу AutoClosedMi.

### POST /incidents/{sysId}/assignment

Тело: `{ "team": "Команда X", "expectedRevision": 12 }`. Ответ 200 — новый полный Snapshot, совместимый с `/snapshot`. Ошибка 409 при конфликте версии или попытке назначить завершённый/закрытый инцидент, 400 при неизвестной команде.
После смены команды прежний персональный исполнитель очищается, обновляется lastAssignmentToTeamDateTime; статус автоматически не меняется. Изменение публикуется в SSE и журнале. Реальный backend должен проверить права пользователя и выполнить проверку версии и запись атомарно.

Рекомендация загружается из `/incidents/{sysId}/analysis`: кандидат с непустыми evidenceIds из завершённых/закрытых сопоставимых случаев показывается первым и предварительно выбирается. Координатор подтверждает назначение. При отсутствии оснований никакая команда автоматически не выбирается. Поле provider отличает rules от llm; сейчас демо использует rules, внешняя модель не подключена.

### GET /problems/clusters

Демо-маршрут: `{ "items": [{ "id": "...", "title": "Сервис X", "reason": "Один затронутый сервис; регистрации в пределах 24 часов", "incidentIds": ["INC1", "INC2"], "sysIds": ["1", "2"] }], "revision": 12, "provider": "rules" }`.
Сейчас UI использует тот же алгоритм на снимке: минимум два активных инцидента, одинаковый непустой сервис или выраженное сходство симптомов заголовка, регистрации не дальше 24 часов друг от друга. Совпадение одного продукта недостаточно. Это проверяемые гипотезы, а не установленные общие причины; автоматического объединения нет.


### Полный пример запроса страницы

```http
GET /api/v1/incidents?page=1&pageSize=9&group=all&priority=4&status=Assigned&sla=soon&sort=deadline
```

Фильтры: priority=4 (в интерфейсе P1), status=Assigned, SLA не более 30 минут. team — точное имя команды, закодированное как URL query. Пустые фильтры не передаются.

Значения SLA: late — операционный срок истёк; soon — положительный остаток не более 30 минут; normal — больше 30 минут; unknown — у операционного инцидента нет срока либо статус неизвестен; research — Research; restored — Resolved; closed — Closed. У Resolved/Closed/Research прежний deadline не делает запись просроченным активным инцидентом.

### Минимум данных в Incident

Для таблицы и карточки: sysId, id, header, description, shortDescription, priorityId/priority, stateId/stateEnum/state, submitDate, deadline, completionDate, assignedGroupName, assignedEmployee, assignedEmployeeLogin, lastAssignmentToTeamDateTime, productName, service. Все остальные поля исходной выгрузки также сохраняются. Отсутствующую команду текущий контракт передаёт пустой строкой, отсутствующий срок — null.
На назначении UI использует точное имя team, совпадающее с assignedGroupName. Переход на teamId потребует согласованного изменения адаптера фронтенда.
Для схемы Analysis все массивы (facts, attention, candidates, missing) обязательны, при отсутствии данных возвращается пустой массив. Кандидаты сортируются от наиболее обоснованного; evidenceIds — реальные номера инцидентов из истории, а не sysId. Анализ всегда привязан к той же revision, что и Snapshot; UI не подставляет рекомендацию другой версии.

### Подключение frontend

Фронтенд использует общий origin с API или полный HTTPS-адрес в VITE_API_BASE_URL. Чтение и поток событий доступны через обычный fetch и EventSource. Для назначения Rust API принимает заголовок `Authorization: Bearer <ключ координатора>`. Ключ задаётся в ASSIGNMENT_TOKEN на сервере. Координатор вводит ключ на экране входа и может сохранить его на устройстве. Назначение автоматически использует этот ключ; ответ 401 очищает текущую сессию и возвращает на экран входа. При пустой серверной настройке API возвращает 403. В потоке событий ключ не требуется.
Backend должен отдавать доступный браузеру JSON/CORS и разрешать нужные методы. Без изменений текущий клиент принимает синхронный Analysis 200 и полный Snapshot 200 после назначения; 202/204 и частичные SSE-дельты потребуют адаптации.

### Сигналы и обновления (актуальный хедер)

В хедере три случая:
- красная карточка: активный критический инцидент (priorityId 4, Assigned/WorkInProgress), которому не назначена команда решения;
- жёлтая карточка: инцидент ожидает распределения строго больше 8 минут;
- жёлтая карточка срока: осталось строго меньше 30% общего времени `(deadline − now) / (deadline − submitDate) < 0.3`. До истечения дедлайна учитываются Assigned/WorkInProgress/Research независимо от команды. После истечения срока карточка показывается только без команды решения. Назначение реальной команды снимает просроченную карточку; красный таймер очереди сохраняется. Просроченная задача без команды остаётся в хедере до назначения команды, завершения или переноса дедлайна за порог 30%; Resolved/Closed исключаются. Некорректные/отсутствующие даты и deadline ≤ submitDate не создают такое предупреждение.

Без команды решения = assignedGroupName пустой либо равен «КЦ ИТ Координаторы Массовых Инцидентов». Для второго случая учитываются Assigned/WorkInProgress/Research. Ожидание считается с lastAssignmentToTeamDateTime, при отсутствии корректной даты — с submitDate; время не придумывается.
На один инцидент выводится одна карточка: критический без команды → ожидание распределения → порог дедлайна. При пороге ровно 30% предупреждения ещё нет. Новая категория срока появляется автоматически при ходе времени или SSE-изменении дат. Звуковой сигнал и колокольчик по-прежнему относятся только к первым двум условиям; предупреждение срока само по себе не звонит. Счётчики групп сохраняют отдельные бизнес-правила.
Увеличенный красный колокольчик появляется с анимацией на 3,2 секунды и скрывается. Звук и анимация срабатывают при новом попадании в условие, смене его типа, обновлении назначения координаторам или дедлайна подходящей карточки; тики таймера не дают повторного сигнала. Первичная загрузка архива не звонит. Отложенный звук отменяется, если подходящих задач больше нет.
Активный хедер продолжает анимацию пустого состояния: мягко пульсирующие кольца и линия сигнала, красный акцент для критических и янтарный для ожидания команды. Справа до трёх уникальных карточек одновременно, без дублирования. Страницы плавно сменяются раз в 10 секунд; стрелки переключают вручную, наведение/фокус останавливают смену. Учитывается prefers-reduced-motion. Фон по всей площади — белые полупрозрачные МТС и клавиши. При отсутствии задач показывается прежняя анимация «Всё под контролем». В «Симуляции» можно очистить только тестовый хедер, добавить критическую/ожидающую задачу и вернуться к данным сервера; эти действия не меняют очередь или JSON и не требуют новых backend-роутов.
Новые записи источника подсвечиваются и появляются в очереди с анимацией 6 секунд; первичная загрузка, смена фильтра и страницы не считаются новым инцидентом. Изменённые поля также подсвечиваются 6 секунд. Всплывающих уведомлений нет.
Звук воспроизводится локальным файлом /sounds/alert-bell.wav через HTMLAudioElement, выключателя нет. Браузеру требуется первое взаимодействие со страницей для воспроизведения.


### Дополнение: фильтры и навигация

GET /incidents дополнительно принимает `priority` (исходный priorityId 1–4), `status` (stateEnum), `sla` (`late`, `soon`, `normal`, `unknown`, `research`, `restored`, `closed`). `team=__unassigned__` — нет назначенной команды. Фильтры комбинируются и применяются до пагинации, SLA вычисляется по времени сервера. Клиент использует те же правила по сохранённому снимку при отсутствии сети. Параметр фильтра называется именно priority, а не priorityId; его значение равно исходному priorityId.
Группы и поиск повторяют макет; фильтры открываются кнопкой рядом с поиском. Массовые сбои доступны отдельным пунктом слева (`#problems`). Звуковых настроек и всплывающих уведомлений нет.


### Уточнение организаторов: группы и источник обращения

`critical` = priorityId 4 + Assigned/WorkInProgress. `high` = priorityId 3 + Assigned/WorkInProgress. Клиентский тип сервиса, urgencyId и impactId не добавляют инцидент в эти группы.
Research (stateId 20) не входит в активные critical/high независимо от приоритета. Он остаётся в research и одновременно в coordinators, если assignedGroupName совпадает с командой координаторов. Исследование не вызывает красную карточку хедера по приоритету и не считается активным сбоем в поиске массовых проблем.
isNeedUp, isMaster, isEffect и остальные флаги сохраняются и показываются в карточке; сами по себе не повышают приоритет.
receivingChannel — источник регистрации: мониторинг, жалоба клиента или обращение сотрудника. Это не ФИО инициатора; initiatorName/initiatorLogin хранятся отдельно. Неизвестные значения отображаются без выдуманной классификации.

### Обновление статуса из ITSM / JSON через SSE

Статус на фронтенде доступен только для просмотра. Отдельного HTTP-метода смены статуса в текущем Rust API нет. Назначение команды не меняет статус.

Импортёр принимает атомарно заменённый полный JSON-массив, сохраняет ревизию и историю в PostgreSQL и отправляет полный `event: snapshot` в `/events/stream?view=web`. Фронтенд сразу заменяет общий снимок. Очередь, открытая карточка (по `sysId`), её история, счётчики групп и хедер пересчитываются из одной ревизии без перезагрузки и закрытия карточки. Пагинация и выбранные фильтры сохраняются. До ответа дополнительного GET /incidents очередь строится из свежего SSE-снимка; HTTP-страница другой ревизии не используется.

`Assigned/0` и `WorkInProgress/2` участвуют в активных приоритетах. `Research/20` исключается из критических/высоких, но может оставаться в ожидании команды больше 8 минут. Если у исследования указан `deadline`, интерфейс показывает живой отсчёт до него и просрочку после его истечения. Серверная категория `sla=research` сохраняется; отображение таймера не меняет правила фильтрации API. Для `Resolved/7` и `Closed/10` числовой таймер равен `00:00:00`, а исходный дедлайн остаётся доступен как плановая дата. Отсутствующий дедлайн отображается как `--:--:--`, а не как ложный нулевой остаток. `Resolved/7` и `Closed/10` убираются из хедера. Возврат в активный статус повторно проверяет условия хедера.

Регрессия проверяется `tests/status-sse.test.mjs`: атомарная замена изолированного JSON → файловый импорт тестового адаптера → один настоящий SSE-поток → нормализация и актуальные представления. Это проверка frontend-контракта; PostgreSQL и Rust importer на vserver проверяются отдельно на запущенном backend.

### Отдельная страница инцидента и возврат

Карточка открывается маршрутом `#incident/{sysId}?from=incidents|events|problems|...`. Исходный экран остаётся смонтированным и скрывается, поэтому возврат стрелкой или кнопкой браузера сохраняет поиск, фильтры, номер страницы и прокрутку. Старые ссылки `#incidents?incident={sysId}` поддерживаются. Данные страницы и истории берутся из общего SSE-снимка по строковому sysId; отдельного редактирования статуса нет. Назначение команды открывает диалог поверх страницы и не закрывает её.

### Вход по ключу координатора

По согласованному временному варианту вход использует существующий `ASSIGNMENT_TOKEN`, а не логин/пароль. Экран входа сохраняет только ключ и время входа. Флажок «Запомнить на этом устройстве» включён по умолчанию: ключ хранится в localStorage, с областью действия по origin и префиксу API. Без флажка ключ остаётся только в памяти текущей вкладки. Пароли и токены в URL не передаются. Выход очищает ключ, локальный снимок и отметки прочтения. Состояние входа синхронизируется между вкладками.

Ключ автоматически передаётся только в `Authorization: Bearer ...` запроса назначения; повторный ввод в диалоге назначения не нужен. Ответ 401 для текущего ключа очищает сессию и возвращает на вход. Ответ старого запроса после нового входа не сбрасывает новую сессию.

Ограничение текущего backend: отдельного метода проверки ключа, входа, refresh или отзыва сессии нет. Поэтому сохранение ключа на экране входа само по себе не проверяет его валидность; сервер проверяет ключ при назначении команды. GET и SSE остаются публичными по текущему контракту. Экран входа — способ сохранить ключ координатора, а не серверная защита операций чтения. Для персональных аккаунтов и полноценной авторизации backend должен отдельно реализовать сессии; предпочтительный постоянный вход — серверная HttpOnly-cookie сессия. Production работает через HTTPS; ключ доступен JavaScript текущего origin, поэтому в интерфейс нельзя внедрять непроверенные скрипты. В локальном режиме `demo` вход не требуется.


### Цвет времени в колонке SLA

Завершённые и закрытые — зелёный `#206650` и `00:00:00`; просрочка — красный `#A61C43`; остаток строго меньше 30% срока от submitDate до deadline — `#79501B`; обычный остаток — `#34546F`. Ровно 30% относится к обычному остатку. Это правила отображения; серверные параметры фильтра SLA не меняются.
